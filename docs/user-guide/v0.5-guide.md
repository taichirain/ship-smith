# 第一部分：快速上手（新手必读）

## 前置检查

开始之前，确保你有：

| 组件 | 要求 |
|------|------|
| **Core API 服务器** | PostgreSQL 12+ |
| **Agent 目标服务器** | Linux、Docker、Docker Compose、Git |
| **你的开发机** | 能访问 Web Panel |

---

## 第一步：创建项目

### 操作步骤

1. 登录 Web Panel
2. 点击 **New Project**
3. 按照向导填写信息
4. 保存显示的 `agent_token`（只会显示一次）

### 需要填写的字段

| 字段 | 示例值 | 说明 |
|------|--------|------|
| Project Name | `my-app` | 随便起个名字 |
| Git Repository | `git@github.com:user/repo.git` | 你的代码仓库 |
| Git Branch | `main` | 默认部署哪个分支 |
| Deploy Workdir | `/opt/my-app` | **服务器上**的目录，必须已存在 |
| Compose File | `docker-compose.yml` | 相对于 Workdir 的路径 |
| Compose Service | `app` | compose 文件中的主服务名 |
| Deploy Strategy | `compose-build` | build=本地构建，pull=拉取镜像 |
| Health Check URL | `http://localhost:8080/health` | 确认应用启动成功 |
| Flags File Path | `/opt/my-app/flags.json` | Feature Flag 文件位置 |

### Deploy Strategy 怎么选？

| 选择 | 场景 |
|------|------|
| ✅ `compose-build` | Dockerfile 在代码仓库里 |
| ✅ `compose-pull` | 镜像已推送到 Docker Hub / 私有仓库 |

## 第二步：安装 Agent

### 在目标服务器上执行

```bash
# 1. 导出凭证
export SHIPSMITH_AGENT_TOKEN="你刚才保存的 token"
export SHIPSMITH_CORE_URL="http://core-host:8000/api/v1"
export SHIPSMITH_WORKDIR="/opt/my-app"  # 与项目配置一致

# 2. 确保工作目录存在
sudo mkdir -p /opt/my-app
sudo chown -R $USER:$USER /opt/my-app

# 3. 启动 Agent
shipsmith-agent
```

### 验证 Agent 是否正常

Agent 启动后会自动上报心跳，在 Web Panel 可以看到：
- 项目详情页 → Agent 状态变为 `online`
- 显示最近心跳时间

## 第三步：环境预检

### 为什么要做预检？

**提前发现问题，避免部署到一半失败。**

### 操作步骤

1. 进入项目详情页
2. 找到 **Agent 环境预检** 区域
3. 点击 **运行预检**
4. 等待 10-30 秒
5. 查看结果

### 结果怎么看？

| 图标 | 状态 | 含义 | 下一步 |
|------|------|------|--------|
| ✅ | 健康 | 所有检查通过 | 可以部署 |
| ⚠️ | 降级 | 有警告，可能影响 | 查看警告详情，决定是否部署 |
| ❌ | 不健康 | 有严重问题 | 必须修复 |

### 常见问题修复

#### 问题：Git 不可用
```bash
# 安装
sudo apt install git   # Ubuntu/Debian
sudo yum install git   # CentOS/RHEL
```

#### 问题：Docker 未运行
```bash
# 启动 Docker
sudo systemctl start docker

# 将当前用户加入 docker 组（免 sudo）
sudo usermod -aG docker $USER
newgrp docker  # 重新加载组配置
```

#### 问题：工作目录不存在
```bash
sudo mkdir -p /opt/my-app
sudo chown -R $USER:$USER /opt/my-app
```

## 第四步：首次部署

### 操作步骤

1. 项目详情页 → 点击 **Deploy**
2. 选择要部署的分支/Commit（可选，默认用 Git Branch）
3. 确认部署
4. 等待...

### 部署过程会做什么？

```
1. 拉取代码    → 从 Git 仓库获取最新代码
2. 检出代码    → 切换到指定分支/Commit
3. 构建/拉取镜像 → build 或 pull
4. 启动容器    → docker compose up
5. 健康检查    → 确认应用正常
```

---

## 第五步：查看结果

### 部署成功 ✅

- 项目状态变为 `healthy`
- 可以查看部署日志
- 可以继续开发或做下一次部署

### 部署失败 ❌

**别急，系统会帮你分析原因：**

1. 进入部署详情页
2. 查看 **失败分析** 区域
3. 系统会告诉你：
   - 失败发生在哪个阶段
   - 可能是什么原因
   - 建议先检查什么
   - 可以执行哪些命令排查

## 配置详解

### 创建项目时的字段

#### Deploy Workdir

这是 Agent 在服务器上执行所有操作的根目录。

**要求：**
- 必须已存在
- Agent 运行用户有读写权限
- 包含 `docker-compose.yml`（或你指定的 compose 文件）

**检查：**
```bash
ls -la /opt/my-app
cat /opt/my-app/docker-compose.yml
```

#### Compose Service

Compose 文件中哪个服务是你的应用主服务？

**用途：**
- 健康检查会检查这个服务
- 回滚时主要关注这个服务

**示例 compose 文件：**
```yaml
services:
  app:          # ← 这就是 Compose Service
    image: my-app
    ports:
      - "8080:8080"
  db:
    image: postgres
```

#### Health Check URL

**为什么重要？**
- 容器启动 ≠ 应用准备好了
- 健康检查确认应用真正可以处理请求

**建议实现：**

在你的应用中添加一个健康检查接口：
- 路径：`/health` 或 `/status`
- 返回：HTTP 200 + JSON
- 内容：`{"status": "healthy"}`

**测试：**
```bash
curl http://localhost:8080/health
```

#### Flags File Path

Feature Flag 文件的位置。

**格式（JSON）：**
```json
{
  "new_feature": true,
  "beta_mode": false
}
```

**在应用中读取：**
```python
import json

with open("/opt/my-app/flags.json") as f:
    flags = json.load(f)

if flags.get("new_feature"):
    # 新功能逻辑
```

## 环境预检说明

### 预检检查什么？

#### 配置类
- Agent Token 是否有效
- Core API 地址是否可访问

#### 工具类
- Git 命令是否可用
- Docker 服务是否运行
- Docker Compose 命令是否可用

#### Docker 类
- 当前用户是否能执行 docker 命令（是否在 docker 组）
- Docker 可用磁盘空间

#### 文件系统类
- Workdir 是否存在
- Workdir 是否可写
- Compose 文件是否存在

#### 网络类
- 能否连接到 Core API
- 能否访问外部网络（Git 仓库、镜像仓库等）

#### 系统资源类
- CPU 使用率
- 可用内存
- 磁盘使用率

## 部署失败排查

### 失败阶段说明

| 阶段 | 含义 | 常见原因 |
|------|------|----------|
| `git_fetch` | 拉取代码失败 | 网络问题、密钥错误、Token 过期 |
| `git_checkout` | 检出代码失败 | 分支不存在、Commit 不存在、文件冲突 |
| `docker_build` | 构建镜像失败 | Dockerfile 错误、依赖问题、磁盘满 |
| `docker_pull` | 拉取镜像失败 | 网络问题、镜像不存在、权限问题 |
| `docker_up` | 启动容器失败 | 端口占用、配置错误、环境变量缺失 |
| `health_check` | 健康检查失败 | 应用启动慢、路径错误、应用崩溃 |
| `precheck` | 预检失败 | 环境检查有未解决的问题 |

### 常见问题排查

#### 代码拉取失败

**排查命令：**
```bash
# 测试 SSH 连接
ssh -T git@github.com

# 手动拉取
cd /opt/my-app
git fetch origin
git status
```

**常见原因：**
- SSH 密钥未配置到 Git 平台
- HTTPS Token 过期
- 网络无法访问 GitHub/GitLab

#### 镜像构建失败

**排查命令：**
```bash
# 手动构建，看完整日志
cd /opt/my-app
docker compose build --no-cache

# 检查磁盘
df -h

# 清理 Docker 空间
docker system prune -f
```

**常见原因：**
- Dockerfile 语法错误
- 依赖包下载失败（网络或源问题）
- 磁盘空间不足

#### 容器启动失败

**排查命令：**
```bash
# 查看容器日志
docker compose logs

# 查看端口占用
netstat -tulpn | grep 8080

# 手动启动，看实时输出
docker compose up
```

**常见原因：**
- 端口被其他进程占用
- compose 文件配置错误
- 环境变量缺失
- 卷挂载路径不存在

#### 健康检查失败

**排查命令：**
```bash
# 查看应用日志
docker compose logs app

# 检查容器是否运行
docker compose ps

# 本地测试健康检查
curl -v http://localhost:8080/health
```

**常见原因：**
- 应用启动需要时间（健康检查超时太短）
- 健康检查路径错误
- 容器端口映射错误
- 应用内部错误

### 系统自动检测的模式

部署失败时，系统会从日志中自动检测：

| 检测到的问题 | 关键词 |
|--------------|--------|
| 权限不足 | `permission denied`, `EACCES` |
| 文件不存在 | `No such file`, `ENOENT` |
| 端口占用 | `address already in use`, `port.*bound` |
| 磁盘满 | `no space left`, `ENOSPC` |
| 网络问题 | `timeout`, `connection refused`, `unreachable` |
| 镜像不存在 | `manifest unknown`, `image not found` |
| Docker 未运行 | `cannot connect to the Docker daemon` |
| 内存不足 | `out of memory`, `OOM` |

## AI 智能分析（可选）

### 什么是 AI 智能分析？

当规则层无法充分解释失败原因时，可以启用 LLM 来分析日志，生成更详细的解释和建议。

> ⚠️ **这是可选功能，不配置不影响任何核心功能。**

### 支持的模型提供商

| 提供商 | 配置值 |
|--------|--------|
| OpenAI | `openai` |
| 智谱 AI | `zhipu` |
| 阿里云千问 | `qwen` |
| OpenRouter | `openrouter` |

### 配置方法

在 Core API 的环境变量中添加：

```env
LLM_ENABLED=true
LLM_PROVIDER=openai
LLM_API_KEY=sk-xxxxx
LLM_MODEL=gpt-4o-mini
```

### 各提供商配置示例

#### OpenAI
```env
LLM_ENABLED=true
LLM_PROVIDER=openai
LLM_API_KEY=sk-xxxxx
LLM_MODEL=gpt-4o-mini
```

#### 智谱 AI
```env
LLM_ENABLED=true
LLM_PROVIDER=zhipu
LLM_API_KEY=xxxxx
LLM_MODEL=glm-4-flash
```

#### 阿里云千问
```env
LLM_ENABLED=true
LLM_PROVIDER=qwen
LLM_API_KEY=sk-xxxxx
LLM_MODEL=qwen-turbo
```

#### 私有部署（OpenAI 兼容）
```env
LLM_ENABLED=true
LLM_PROVIDER=openai
LLM_API_KEY=sk-xxxxx
LLM_API_BASE=http://localhost:8000/v1
LLM_MODEL=your-model-name
```

### AI 分析会提供什么？

当 LLM 启用时，失败分析会额外包含：
- 根本原因分析
- 最可能的问题
- 详细解释
- 建议先检查的项目
- 建议执行的诊断命令

### 隐私说明

- 启用后，日志内容会发送给 LLM 提供商
- 如果日志包含敏感信息，建议不要启用
- 可以使用支持本地部署的模型

## 回滚操作

### 什么时候需要回滚？

- 新部署导致服务不可用
- 发现严重 Bug
- 功能不符合预期

### 操作步骤

1. 进入项目详情页
2. 找到 **部署历史**
3. 选择一次 **成功的** 旧部署
4. 点击 **Rollback to this**
5. 确认回滚

### 回滚会做什么？

1. 检出旧版本代码
2. 构建/拉取对应镜像
3. 启动旧版本容器
4. 运行健康检查

### 注意事项

- 回滚本质上也是一次部署，会有部署记录
- 回滚后，项目会使用旧版本代码
- 如果涉及数据库迁移，需要手动处理

## 运行手册

### 什么是 Runbook？

Runbook 是项目的"说明书"，记录项目相关的重要信息，方便团队协作和日后维护。

### 建议记录的内容

| 字段 | 记录什么 |
|------|----------|
| 项目说明 | 项目用途、技术栈、关键依赖 |
| 发布注意事项 | 发布前检查、发布流程、回滚方案 |
| 常见故障 | 历史故障、原因、解决方法 |
| SSH 访问 | 服务器连接信息 |
| 管理后台 | 常用链接 |
| 监控面板 | Grafana、Prometheus 等 |
| 日志系统 | ELK、Loki 等 |

### 填写示例

**项目说明：**
```
这是一个基于 FastAPI 的后端服务。
技术栈：FastAPI + SQLAlchemy + PostgreSQL
```

**发布注意事项：**
```
发布前检查：
1. 数据库迁移是否已准备
2. Feature Flag 是否同步
3. 通知相关团队

回滚方案：选择上一次成功部署，点击回滚
```

**常见故障：**
```
现象：健康检查返回 500
原因：数据库连接池耗尽
解决：重启服务释放连接，检查连接泄漏
```

## 常见问题

### Agent 问题

**Q: Agent 连不上 Core API？**
```bash
# 测试网络
curl http://core-host:8000/api/v1/health

# 检查环境变量
echo $SHIPSMITH_CORE_URL
echo $SHIPSMITH_AGENT_TOKEN
```

**Q: 执行 docker 命令需要 sudo？**
```bash
sudo usermod -aG docker $USER
newgrp docker
docker ps  # 验证
```

### 部署问题

**Q: 镜像构建慢或卡住？**
```bash
# 检查网络
ping docker.io

# 检查磁盘
df -h

# 清理缓存
docker system prune -a -f
```

**Q: 容器启动后立即退出？**
```bash
# 看日志
docker compose logs

# 手动启动看输出
docker compose up
```

**Q: 健康检查一直失败？**
```bash
# 延长健康检查超时时间
# 或检查应用是否真的正常
curl http://localhost:8080/health
```

### 系统问题

**Q: 磁盘满了？**
```bash
df -h

# 清理 Docker
docker system prune -a -f

# 找大文件
sudo find / -type f -size +100M 2>/dev/null
```

**Q: 内存不足？**
```bash
free -h

# 看谁占内存
top

# 检查 OOM（内存溢出）
dmesg | grep -i oom
```
