# ShipSmith v0.4 规划：从凑合能用到真正好用

> 版本：v0.4 规划草案  
> 日期：2026-05-08  
> 目标：把 ShipSmith 从“能管理部署”推进成“中小 SaaS 团队愿意每天打开的运维工具”

---

## 1. 这次要解决的问题

`v0.3` 之后，ShipSmith 的核心闭环已经比较完整：
- 可以建项目、改配置、接 Agent、跑部署
- 可以看部署日志、看健康状态、接 webhook
- 有基础的 Feature Flag 管理

这说明它已经不是 demo 了。

但如果目标是给 **中小 SaaS 平台做运维工具**，现在还差一层很关键的体验：

**不是“有没有这个功能”，而是“出问题时是不是顺手，日常巡检时是不是省脑子”。**

`v0.4` 的核心目标不是继续堆更强的大功能，而是补齐一批“小而高频、组合起来非常好用”的运维能力。

一句话定义：

**让 ShipSmith 从部署控制台，升级成轻量运维工作台。**

---

## 2. v0.4 的产品判断

对于中小 SaaS 团队，真正高频的运维动作通常只有这些：
- 早上打开一眼看哪些项目异常
- 收到失败通知后快速定位项目和原因
- 看最近是不是有人发过版、改过开关、配过 webhook
- 出事后快速 retry、rollback、复制信息、拉日志
- 给自己或同事留一点 runbook 和备注，避免每次靠记忆

所以 `v0.4` 不该优先做这些：
- 复杂发布策略
- 多层权限系统
- 大而全监控平台
- 自建日志检索 / tracing / APM

`v0.4` 应该优先做的是：
- **全局可见**
- **通知及时**
- **操作顺手**
- **排障省脑子**
- **知识留得住**

---

## 3. v0.4 核心方向

按价值分为三档：`必须做 / 很值 / 可以后放`。

## 3.1 必须做

### A. 全局运维首页

目标：让用户打开首页就知道“今天要处理什么”。

建议补齐：
- 全局概览页，不再只有项目列表
- 顶部摘要卡片：
  - 项目总数
  - healthy 数量
  - degraded / unhealthy 数量
  - offline 数量
  - 近 24 小时失败部署数
- 异常项目列表：
  - Agent 离线
  - 健康检查失败
  - 最近一次部署失败
  - 长时间无心跳
- 最近变更流：
  - 最新 deployment / rollback
  - 最新 flag 变更
  - 最新 webhook 触发

为什么重要：
- 现在更像“点进某项目后才能看”
- 运维工具第一屏必须先告诉用户“哪儿不对劲”

完成定义：
- 不点进项目，也能先知道今天最值得看的 3 到 5 个异常

### B. 通知系统

目标：让问题主动来找你，而不是等你手动刷新页面。

建议补齐：
- 通知渠道先做轻量版：
  - 通用 webhook
  - 飞书机器人
  - Slack webhook
- 首批通知事件：
  - deployment success
  - deployment failed
  - agent offline
  - app health degraded / unhealthy
  - health recovered
- 支持项目级开启/关闭
- 支持最小去噪：
  - 同类事件合并
  - 恢复通知
  - 冷却时间

为什么重要：
- 中小 SaaS 团队最缺的是“及时知道出事了”
- 这是运维工具从“面板”变成“值班帮手”的关键一步

完成定义：
- 一次失败部署或离线事件，能在 1 分钟内推到指定渠道
- 不会因为连续失败而刷屏到不可用

### C. 项目时间线

目标：把一个项目最近发生的关键动作串起来。

建议补齐：
- 项目详情页增加 timeline 区块
- 聚合展示：
  - deploy / rollback
  - flag create / toggle / archive
  - project config update
  - webhook trigger
  - agent online / offline
- 每条记录带：
  - 时间
  - 动作类型
  - 操作者或来源
  - 简短摘要

为什么重要：
- 排障时第一问题通常是：最近到底谁动过它
- 现在信息散在多块区域里，不利于回放上下文

完成定义：
- 打开项目详情页，5 秒内看懂最近一天内发生了什么

### D. 快捷运维动作

目标：减少重复的低价值点击和复制粘贴。

建议补齐：
- 一键 `retry deployment`
- 一键 `rollback to last success`
- 一键复制：
  - webhook endpoint
  - agent 启动命令
  - 当前 commit
  - 最近错误码
- 一键下载最近部署日志
- 一键打开 health check url

为什么重要：
- 这些都不是大功能，但它们最能直接提升“顺手感”

完成定义：
- 常见处理动作控制在 1 到 2 次点击内完成

## 3.2 很值，建议紧接着做

### E. 项目列表升级成真正的工作列表

目标：项目页不只是目录，而是可以筛异常、排优先级。

建议补齐：
- 搜索项目名 / repo
- 按状态筛选：healthy / degraded / unhealthy / offline
- 按“最近失败”“最近部署”“最近无心跳”排序
- 显示更多摘要列：
  - 最近部署状态
  - 最近部署时间
  - 当前 commit 简写
  - 最近心跳时间

完成定义：
- 项目一多时，列表页仍然能当作日常巡检入口

### F. 轻量告警中心

目标：让异常不只是消息流，而是可追踪对象。

建议补齐：
- 系统内保留 recent alerts 列表
- 告警状态：
  - open
  - acknowledged
  - resolved
- 支持简单“忽略 1 小时 / 今天不再提示”

为什么值：
- 中小团队不一定要 PagerDuty，但至少需要一个面板内的异常收纳区

完成定义：
- 用户能分清“还没处理的异常”和“已经知道但暂时不处理的异常”

### G. 运行备注与 Runbook

目标：让项目知识跟着项目走，不靠脑子记。

建议补齐：
- 项目级备注
- 排障提示
- 发布注意事项
- 常用地址：
  - admin
  - health
  - logs
  - metrics
  - SSH / jump host 说明

为什么值：
- 对中小团队来说，这比高级权限系统更实际

完成定义：
- 新人或未来的自己，打开项目页就知道怎么处理这个服务

### H. 健康趋势的轻量历史

目标：看得到“这是刚坏的，还是一直在抖”。

建议补齐：
- 24h / 7d 简图
- 指标只保留最关键的：
  - 心跳是否连续
  - app health 状态
  - response time
  - 最近部署点位

为什么值：
- 运维判断经常依赖趋势，而不是某个时间点的瞬时状态

完成定义：
- 用户能一眼看出这次异常是偶发还是持续

## 3.3 可以后放

### I. 多环境视图

建议补齐：
- `prod / staging` 标签
- 同仓库多个项目并排对比

### J. Agent 版本治理

建议补齐：
- Agent 当前版本展示
- 版本过旧提醒
- 升级建议

### K. 数据保留与清理策略

建议补齐：
- 心跳清理策略
- 日志保留期限
- webhook payload 保留期限

---

## 4. v0.4 不该做成什么样

为了保持产品方向清晰，建议明确避免以下倾向：

### 4.1 不要过早平台化

不要在这一版做太重的：
- 多租户组织模型
- 复杂 RBAC
- 工单系统
- 自定义工作流引擎

### 4.2 不要监控系统化

不要把 ShipSmith 做成另一个 Prometheus / Grafana / Datadog。

它应该只做：
- 和部署强相关的健康信号
- 足够值班判断的轻量趋势
- 足够排障的上下文聚合

### 4.3 不要只做“更多按钮”

如果一个新功能不能明显减少：
- 刷页面次数
- SSH 登录次数
- 排障心智负担

那它大概率不是当前最优先项。

---

## 5. 推荐的 v0.4 版本切法

### v0.4.0

聚焦“先看见问题”：
- 全局运维首页
- 项目列表筛选与排序
- 项目时间线

### v0.4.1

聚焦“问题主动找你”：
- 通知系统
- 恢复通知
- 基础降噪
- 面板内 recent alerts

### v0.4.2

聚焦“处理问题更顺手”：
- retry / rollback 快捷动作
- 复制与下载类小工具
- runbook / 备注 / 常用地址

### v0.4.3

聚焦“判断问题更从容”：
- 健康趋势
- 近期部署点位叠加
- Agent 版本信息

---

## 6. 我建议的实际优先顺序

如果只按“投入产出比”排，我建议是：

1. 全局运维首页
2. 项目时间线
3. 通知系统
4. 项目列表升级
5. 快捷运维动作
6. Runbook / 备注
7. 轻量告警中心
8. 健康趋势

原因：
- 1 到 3 先解决“看见问题”
- 4 到 6 再解决“操作顺手”
- 7 到 8 最后补“沉淀和判断”

---

## 7. v0.4 完成定义

满足下面这些条件时，可以认为 ShipSmith 从“凑合能用”进入“好用”阶段：

- 用户每天先看首页，而不是逐个点项目排查
- 部署失败、Agent 离线、健康异常能主动通知
- 一个项目最近发生了什么，可以在一条时间线里看清楚
- 常见处理动作不需要再依赖手工复制和来回切页面
- 项目页能承载最基本的运维知识，而不是只放机器状态

---

## 8. 一句话结论

`v0.4` 最值得做的，不是把单个功能变得非常强，而是把一组 **小而高频的运维体验** 补齐。

对中小 SaaS 团队来说，真正好用的标准不是“功能大全”，而是：

**出问题时第一时间知道，打开页面能快速看懂，点两下就能处理。**
