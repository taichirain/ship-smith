# ShipSmith v0.3 开发任务清单

> 版本：v0.3 执行清单  
> 日期：2026-05-08  
> 关联文档：`docs/V0.3-PLAN.md`

---

## 1. 使用方式

这不是产品文档，而是开发落地清单。

设计目标：
- 按 `API / Agent / Web / DB / Test` 拆分
- 每项尽量是可独立交付的小任务
- 每项都附上“完成定义”，方便你后面逐项验收

建议执行节奏：
- 先做 `v0.3.0`
- 做完一轮就跑一次 smoke
- 再进入下一小版本

## 2. v0.3.0

目标：先解决“能稳定接入和执行”。

### 2.1 项目配置可维护

#### DB
- [ ] 评估是否需要给 `projects` 表补充 webhook secret、环境标签等字段
- [ ] 如需新增字段，补一版 migration

完成定义：
- 数据模型能覆盖项目编辑与 webhook 安全配置

#### API
- [ ] 增加 `ProjectUpdate` schema
- [ ] 增加 `PATCH /api/v1/projects/{id}`
- [ ] 增加 `POST /api/v1/projects/{id}/rotate-agent-token`
- [ ] 返回新的 agent token 时只返回一次，旧 token 立即失效
- [ ] 为项目编辑接口补充基础校验

完成定义：
- 项目可修改核心部署字段
- token 可轮换且旧 token 无法再访问 agent 接口

#### Web
- [ ] 项目详情页增加“编辑项目配置”表单
- [ ] 项目详情页增加“重置 Agent Token”操作
- [ ] 项目详情页增加 Agent 接入信息展示区
- [ ] 重置 token 后展示一次性复制区域

完成定义：
- 用户不改数据库也能修正项目配置
- 用户能在面板完成 agent 重新接入

### 2.2 Webhook 安全与触发规则

#### DB
- [ ] 为 `projects` 增加 webhook secret 字段
- [ ] 如要做幂等去重，增加 webhook deliveries 表或等价存储

完成定义：
- 项目层面可保存 webhook 验证信息和去重记录

#### API
- [ ] GitHub webhook 增加签名校验
- [ ] GitLab webhook 增加 token/签名校验
- [ ] 增加分支过滤，只允许匹配 `project.git_branch`
- [ ] 忽略 ping、删除分支、空提交等无效事件
- [ ] 使用 delivery id / event id 做幂等去重
- [ ] 明确“进行中任务时”的 webhook 策略
  建议：直接返回 `created=false`，不重复创建 deployment

完成定义：
- 错误签名请求返回 401/403
- 非目标分支不触发部署
- 同一 delivery 重放不会产生重复 deployment

#### Web
- [ ] 项目详情页展示 webhook endpoint
- [ ] 项目详情页支持填写/更新 webhook secret
- [ ] 用简短文案说明 GitHub/GitLab 的配置方法

完成定义：
- 用户能从面板抄配置，不必回 README 翻找

### 2.3 部署任务卡死兜底

#### DB
- [ ] 为 `deployments` 增加任务租约或活跃字段
  例如：`lease_expires_at` / `last_heartbeat_at` / `failure_phase`
- [ ] 评估是否增加 `cancel_requested_at`

完成定义：
- 数据层能表示“任务还活着”与“任务已失联”

#### API
- [ ] `start_task` 时写入租约起点
- [ ] `append_task_logs` 或专用心跳接口刷新任务活跃时间
- [ ] `finish_task` 返回更细的失败信息
- [ ] 增加后台清理逻辑或管理命令
  作用：将长期失活的 `running` 任务标记为失败
- [ ] 区分 `deploy_failed` 与 `healthcheck_failed`

完成定义：
- 不会存在长期挂死在 `running` 的任务
- 失败时能看出是命令失败还是健康检查失败

#### Agent
- [ ] 执行任务期间定期刷新任务活跃状态
- [ ] 若部署流程异常退出，尽量上报最终失败状态
- [ ] 若健康检查失败，单独返回对应错误码

完成定义：
- Agent 在长时间 build/pull 期间不会被误判成卡死

#### Web
- [ ] 部署状态 badge 增补更明确的文案或颜色
- [ ] 部署详情页展示失败阶段、错误码、最后活跃时间

完成定义：
- 用户能看出任务是“正在跑”还是“跑丢了”

## 3. v0.3.1

  建议：`GET /api/v1/projects/{id}/heartbeats`
- [ ] 统一健康状态映射规则

- [ ] 在状态接口中返回最近快照摘要
  包含：CPU、内存、磁盘、容器摘要、最近心跳时间、当前 commit

#### Agent

- [ ] 补齐容器摘要字段
  例如：容器总数、运行中数量、异常容器名
- [ ] 补齐健康检查结果字段
  例如：status code、timeout、错误摘要

完成定义：
- heartbeat 数据格式稳定，前端可以可靠展示

#### Web
- [ ] 项目详情页增加“Health”区域
- [ ] 展示最近心跳时间
- [ ] 展示 CPU / 内存 / 磁盘

## 6. 建议开发顺序

建议严格按下面顺序推进：

1. 项目编辑 + token 轮换
2. webhook secret + 签名 + 分支过滤 + 幂等
3. deployment 活跃租约 + running 卡死兜底
4. 健康状态接口 + 健康看板
5. 部署日志增量轮询 + 详情页刷新
6. flag 删除/归档 + 快照
7. agent bootstrap + 自检
8. API tests + agent tests + smoke

原因：
- 前 3 项解决系统可靠性
- 4 到 5 解决观测与排障
- 6 到 8 解决长期维护成本
