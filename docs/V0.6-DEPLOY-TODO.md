# ShipSmith v0.6 开发任务清单

> 版本：v0.6 执行清单
> 日期：2026-05-09
> 关联文档：`docs/V0.6-DEPLOY-PLAN.md`

---

## 1. 使用方式

这份文档只做一件事：

**把 `v0.6` 的“多机部署最小闭环”拆成可执行任务。**

原则：
- 不引入 SSH 控制链路
- 不把 v0.6 做成完整编排平台
- 优先保证数据模型清晰、状态可见、失败可解释
- 尽量复用现有 Agent 本机执行模型

建议节奏：
- 先做 `v0.6.0`
- 先打通多目标项目和部署汇总
- 再补 `rolling` 策略和交互细节

## 2. v0.6.0

目标：让一个项目能绑定多台机器，并能完成一次多机部署。

### 2.1 数据模型重构

#### DB
- [ ] 新增 `project_targets` 表
  建议字段：
  - `id`
  - `project_id`
  - `agent_id`
  - `name`
  - `role`
  - `enabled`
  - `order_index`
  - `created_at`
  - `updated_at`
- [ ] 新增 `deployment_targets` 表或等价执行表
  建议字段：
  - `id`
  - `deployment_id`
  - `project_target_id`
  - `agent_id`
  - `status`
  - `commit_hash`
  - `started_at`
  - `finished_at`
  - `error_code`
  - `error_message`
- [ ] 为目标级执行日志确定归属关系
  建议优先复用现有 `deployment_logs`，增加目标关联字段
- [ ] 评估 `projects.agent_id` 的迁移策略
  建议：
  - v0.6 先保留字段用于兼容读取
  - migration 时自动回填一个默认 target

完成定义：
- 老项目升级后不会丢失 Agent 绑定关系
- 一个项目可以稳定关联多台机器

#### Migration
- [ ] 编写 migration，给历史项目生成默认 target
- [ ] 为 `project_targets(project_id, enabled, order_index)` 增加必要索引
- [ ] 为 `deployment_targets(deployment_id, status)` 增加必要索引

完成定义：
- 从单机模型升级到多机模型后，现有数据可继续使用

### 2.2 Schema 与枚举

#### Config / API Schema
- [ ] 增加 `DeployMode` 或等价枚举
  建议值：
  - `all-at-once`
  - `rolling`
- [ ] 增加 `ProjectTargetCreate` / `ProjectTargetUpdate` / `ProjectTargetResponse`
- [ ] 增加 `DeploymentTargetResponse`
- [ ] 扩展部署详情返回结构，包含目标级执行明细

完成定义：
- 前后端和 API 文档都能明确表达“项目级部署”和“目标级执行”

## 3. v0.6.1

目标：补齐项目目标管理能力。

### 3.1 项目目标管理 API

#### API
- [ ] 增加项目目标列表接口
  建议：`GET /api/v1/projects/{id}/targets`
- [ ] 增加项目目标创建接口
  建议：`POST /api/v1/projects/{id}/targets`
- [ ] 增加项目目标更新接口
  建议：`PATCH /api/v1/projects/{id}/targets/{target_id}`
- [ ] 增加项目目标删除或禁用接口
  建议优先支持 `enabled=false`，避免直接硬删除
- [ ] 增加目标顺序调整能力
  建议支持更新 `order_index`

#### 校验
- [ ] 同一项目下 `agent_id` 不可重复绑定
- [ ] `rolling` 顺序字段必须稳定可排序
- [ ] 至少保留 1 个 enabled target 才允许项目可部署

完成定义：
- 用户可以在一个项目下维护多台机器，而不是拆项目管理

### 3.2 Agent 绑定与兼容策略

#### API / 服务层
- [ ] 保留原有单项目创建流程的兼容行为
  建议：
  - 创建项目时仍生成默认 `agent_id`
  - 同时自动创建首个 target
- [ ] 梳理 heartbeat 上报时 target 归属方式
- [ ] 明确 target 与 project status 的聚合逻辑

完成定义：
- 新项目和老项目都能平滑进入多 target 模型

### 3.3 Web

#### Web
- [ ] 项目设置页新增“部署目标”区块
- [ ] 支持新增目标
- [ ] 支持编辑目标名称、启用状态、顺序
- [ ] 展示每个目标的 agent id 和最近在线状态
- [ ] 如果项目只有一个目标，界面仍保持简洁，不显得过度复杂

完成定义：
- 用户能在页面上直观看到“这个项目部署到哪些机器”

## 4. v0.6.2

目标：让多机部署真正跑起来，并先支持并行策略。

### 4.1 多目标部署创建

#### API / 服务层
- [ ] 扩展项目部署创建接口，支持传入部署模式
- [ ] 创建 deployment 时，同时创建所有目标级执行记录
- [ ] 汇总记录初始状态定义清楚
  建议：
  - project deployment: `queued`
  - deployment target: `queued`
- [ ] 仅对 enabled targets 创建执行记录

完成定义：
- 一次部署请求能映射成“1 条汇总记录 + N 条目标记录”

### 4.2 Agent 任务分发

#### API / 服务层
- [ ] 改造 Agent 拉任务逻辑，使其领取目标级任务而非项目级唯一任务
- [ ] 保证 Agent 只能领取属于自己 `agent_id` 的目标任务
- [ ] 调整任务开始、日志上报、任务完成接口，关联到目标级执行
- [ ] 汇总 project deployment 状态
  建议规则：
  - 全部成功 => `success`
  - 任一失败 => `failed`
  - 存在运行中 => `running`

完成定义：
- 多个 Agent 可以围绕同一 deployment 独立执行自己的本机任务

### 4.3 部署详情与状态汇总

#### API
- [ ] 扩展部署详情接口，返回：
  - deployment 基本信息
  - deploy mode
  - 目标执行列表
  - 每个目标的状态、错误、时间、commit
- [ ] 如日志仍走统一表，提供按目标过滤日志的能力

#### Web
- [ ] 部署详情页展示汇总状态
- [ ] 列出所有目标执行卡片或表格
- [ ] 支持查看单目标日志
- [ ] 明确展示：
  - 成功台数
  - 失败台数
  - 运行中台数

完成定义：
- 用户可以清楚看懂“这次是整体失败，还是某一台失败”

## 5. v0.6.3

目标：补齐 `rolling` 部署策略。

### 5.1 rolling 编排逻辑

#### API / 服务层
- [ ] 按 `order_index` 顺序放行目标任务
- [ ] 当前目标成功前，不允许下一个目标变为可领取状态
- [ ] 任一目标失败后，默认停止后续目标
- [ ] 为被停止的后续目标定义明确状态
  建议：
  - `blocked`
  - 或复用 `cancelled`，但要保证语义清楚

完成定义：
- `rolling` 行为稳定、可预测，不存在多台机器抢跑

### 5.2 状态表达

#### API / Web
- [ ] 在部署详情页明确区分：
  - 已完成
  - 当前执行中
  - 尚未开始
  - 因上游失败被阻塞
- [ ] 在 deployment 列表中展示 deploy mode
- [ ] 生产环境默认推荐 `rolling`

完成定义：
- 用户一眼能看懂 `rolling` 目前卡在哪一台

## 6. v0.6.4

目标：把边界和失败体验补齐，避免误解成“完整编排平台”。

### 6.1 交互与文案

#### Web
- [ ] 在部署弹窗中明确说明两种策略差异
- [ ] 对多目标项目增加风险提示
  例如：
  - 并行更快，但同时失败面更大
  - 顺序更稳，但发布时间更长
- [ ] 在没有多目标时，不展示过多编排概念

完成定义：
- 用户理解自己选择的是“并行部署”还是“顺序部署”

### 6.2 Runbook 与排障

#### Web / API
- [ ] 在项目 runbook 中预留“多机发布注意事项”
- [ ] 部署失败时，优先指出失败目标
- [ ] 如果是 `rolling`，明确指出是第几台机器阻塞了后续发布

完成定义：
- 多机失败时，用户先知道该去看哪台机器，而不是被汇总状态误导

### 6.3 文档

#### Docs
- [ ] 更新 README 中项目架构描述
- [ ] 更新 quickstart，说明单机和多机的差异
- [ ] 更新 architecture 文档，补充 project target 和 deployment target 模型
- [ ] 明确写出 v0.6 不支持 SSH 和高级发布编排

完成定义：
- 产品边界在文档层面和实现层面保持一致

## 7. 验收清单

- [ ] 老项目升级后自动生成默认 target
- [ ] 一个项目可以绑定 2 到 5 台机器
- [ ] 可以发起一次 `all-at-once` 多机部署
- [ ] 可以发起一次 `rolling` 多机部署
- [ ] 部署详情页能看到每台机器的执行状态和日志
- [ ] 某一台失败时，整体和单机状态都表达清楚
- [ ] 全流程不引入 SSH 执行链路

## 8. 建议优先级

建议开发顺序：

1. 数据模型和 migration
2. 项目目标管理 API
3. 多目标部署创建与状态汇总
4. 部署详情页目标级展示
5. `rolling` 策略
6. 文档与交互补齐

如果中途要缩范围，最后一批可以延后的是：
- 更细的目标排序交互
- 更丰富的失败文案
- 文档里的多场景示例

不能缩掉的是：
- target 数据模型
- 目标级执行状态
- 部署汇总逻辑
- `all-at-once` 最小闭环
