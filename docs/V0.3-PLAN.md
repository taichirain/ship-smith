# ShipSmith v0.3 能力补齐规划

> 版本：v0.3 规划草案  
> 日期：2026-05-08  
> 目标：在 v0.2 MVP 已打通最小闭环的基础上，补齐“可稳定自用”的关键能力

---

## 1. 这份文档解决什么问题

`v0.2` 已经完成了一个可演示、可跑通的最小闭环：
- 有项目管理、部署任务、回滚、Feature Flag、Agent 心跳、基础 Web 面板
- Core / Agent / Web / SDK 的边界已经建立
- 单项目、单机、Docker Compose 场景已经具备基本可用性

但从当前实现看，系统还偏“能工作”，还没完全达到“敢长期拿来管自己的线上服务”的程度。

`v0.3` 的重点不是加很多新概念，而是补齐以下三类缺口：
- 配置与接入能力还偏硬编码，缺少真正的项目接入闭环
- 任务执行与状态反馈还偏粗糙，失败可见性和运行可控性不够
- 面板与 API 还只有最小操作集，缺少日常运维真正会用到的能力

一句话定义 `v0.3`：

**从“能部署一次”升级到“能长期、自信地管理几个真实项目”。**

---

## 2. 当前 v0.2 实际完成度

结合当前仓库实现，`v0.2` 已完成的部分大致如下。

### 2.1 已有能力

- 项目创建、项目列表、项目详情页
- 手动部署、手动回滚、部署历史、部署日志查看
- Agent 轮询任务、上报日志、上报心跳、回写部署结果
- 全局 Feature Flag 创建、切换、审计记录
- GitHub / GitLab Webhook 触发部署
- Node SDK 本地读取 flags
- Agent 打包分发脚本与基础运行方式

### 2.2 当前明显短板

- 项目配置只支持创建，不支持编辑、校验、重新生成 Agent 凭证
- Webhook 没有签名校验、分支过滤、去重和更明确的触发策略
- 部署状态模型较简单，缺少取消、超时、重试、卡死兜底
- 健康与心跳已上报，但面板没有形成真正的“健康看板”
- 日志只能事后看详情，运行中刷新、分阶段视图、失败定位还不够
- Feature Flag 只有布尔开关，没有环境隔离、删除/归档、版本快照
- Agent 接入仍偏手工，缺少复制即用的 bootstrap 指引
- 缺少系统级测试、接口契约校验和最基本的生产化验收

所以 `v0.3` 不适合继续横向铺很多能力，而应该先把这些纵向链路补完整。

---

## 3. v0.3 目标定义

### 3.1 产品目标

让一个独立开发者可以：
- 接入 2 到 5 个真实项目
- 稳定使用手动部署和 webhook 自动部署
- 在失败时快速判断是代码问题、容器问题、Agent 问题还是健康检查问题
- 在面板上完成日常大部分操作，而不是频繁回服务器手工排查

### 3.2 非目标

`v0.3` 仍然不做这些事：
- 多机编排、滚动发布、蓝绿、金丝雀
- 百分比灰度、用户分群、实验平台
- 多租户 SaaS 化
- 完整监控告警平台
- 复杂权限系统和组织协作体系

## 4. v0.3 核心补齐项

下面按优先级分为 `P0 / P1 / P2`。

## 4.1 P0：必须补齐，决定 v0.3 是否成立

### A. 项目配置管理闭环

目标：项目不再是“一次性创建记录”，而是“可维护的部署配置”。

建议补齐：
- 支持编辑项目配置
- 支持更新 `git_branch` / `deploy_strategy` / `compose_file` / `compose_service`
- 支持更新 `healthcheck_url` / `timeout` / `flags_file_path`
- 支持展示 Agent 接入信息
- 支持重置 Agent Token
- 支持项目级只读“接入说明”

为什么优先：
- 当前项目一旦填错，面板里无法修正，真实使用时会立刻卡住
- Agent Token 只生成一次，不利于重新接入或泄露后的处置

验收标准：
- 新建项目后可在面板修改核心配置并立即生效
- 可以重新生成 token，旧 token 失效，新 token 生效
- 用户能在项目详情页直接拿到 Agent 启动所需参数

### B. 部署任务可控性

目标：部署失败时有明确信号，部署运行时有更稳定的状态机。

建议补齐：
- 增加任务超时机制
- 增加 `cancelling / cancelled` 或最少 `cancelled` 状态落地
- 增加 Agent 领取任务后的“租约”或“最后活跃时间”概念
- 对长期 `running` 且 Agent 心跳断开的任务做异常标记
- 区分 `deploy failed` 与 `health check failed`
- 在部署记录里补充阶段耗时、失败阶段、最终错误摘要

为什么优先：
- 现在最怕的不是失败，而是“卡住但不知道是否还在跑”
- 一旦真机网络波动或 Agent 退出，当前状态机会留下不干净的运行态

验收标准：
- 任务超时后能自动结束为明确失败态
- 面板能看出任务卡在哪个阶段
- Agent 异常退出不会让项目永久停留在 `running`

### C. 健康看板成形

目标：把已有 heartbeat 数据变成可以日常看的健康视图。

建议补齐：
- 项目详情页展示最近心跳时间、CPU、内存、磁盘、容器摘要
- 展示最近一次成功部署版本与当前健康状态
- 健康状态规则明确化：`healthy / degraded / offline / unknown`
- 展示健康检查失败原因或最近错误
- 项目列表页增强状态可读性，而不是只显示一个 badge

为什么优先：
- 当前数据库和 Agent 已有这部分基础，但用户价值还没有真正露出来

验收标准：
- 用户无需登录服务器，也能判断“服务在线但健康失败”还是“Agent 已离线”
- 项目列表页可以快速筛出异常项目

### D. Webhook 安全与触发规则

目标：Webhook 可以放心打开，而不是仅做演示。

建议补齐：
- GitHub / GitLab webhook 签名校验
- 分支过滤，只允许命中项目配置分支
- 忽略明显无效事件
- 用 delivery id / event id 做幂等去重
- 明确并实现“进行中任务时如何处理新 webhook”

为什么优先：
- 当前 webhook 基本无防护，线上可用性和安全性都不够

验收标准：
- 未签名或签名错误请求被拒绝
- 非目标分支 push 不会触发部署
- 重复投递不会创建多条重复部署

## 4.2 P1：强烈建议补齐，决定日常使用体验

### E. 部署观测体验

建议补齐：
- 部署详情页自动刷新
- 运行中日志实时轮询
- 按 phase 分组显示日志
- 在列表页直接看到最近失败原因
- 支持复制部署命令摘要、commit、错误码

价值：
- 这是控制台最常用的页面，体验差会直接逼用户回终端

### F. Agent 接入体验

建议补齐：
- 项目创建后自动生成一段 Agent 安装/启动命令
- 提供 `shipsmith.yaml` 模板回填或下载
- 提供 Agent 自检命令，例如检查 `git` / `docker` / 权限 / flags 路径
- 在面板展示“从未连上 / 已连上 / 最近离线”

价值：
- 当前接入知识散落在 README 和代码约定里，新项目接入仍偏手工

### G. Feature Flag 管理补完

建议补齐：
- 支持删除或归档 flag
- 展示 flag 最近更新时间与操作者
- 按项目输出当前 flags 快照
- Agent 同步接口增加版本说明与当前生效版本展示

价值：
- 现在能开关，但还不算真正的“可管理”

### H. 基础测试与验收脚本

建议补齐：
- API 层最小集成测试：登录、建项目、部署、回滚、flags、webhook
- Agent 关键路径测试：任务领取、日志上传、finish 更新
- 一个本地 smoke 脚本，串起 core + db + sample project

价值：
- v0.3 如果没有最小测试网，后面每次改状态机都会很危险

## 4.3 P2：可选增强，放得下就做

### I. 审计与运维细节

建议补齐：
- 项目配置修改审计
- Deployment filter/search
- 保留最近 N 天 heartbeat，支持归档或清理策略

### J. 多环境雏形

建议补齐：
- 允许同仓库创建多个项目实例，如 `app-prod` / `app-staging`
- 面板上明确区分环境标签

说明：
- 这不等于正式做多环境体系，只是给常见自用场景留出空间

## 5. 推荐的 v0.3 版本切法

如果你想把这阶段做得更稳，我建议不要一次性“全补齐”，而是拆成三个小里程碑。

### v0.3.0

聚焦“能稳定接入和执行”：
- 项目配置可编辑
- Agent Token 可重置
- Webhook 签名 + 分支过滤
- 部署超时和异常 running 兜底

### v0.3.1

聚焦“能清楚看见系统状态”：
- 健康看板
- 部署详情自动刷新
- 日志分阶段展示
- 列表页失败摘要

### v0.3.2

聚焦“能长期维护”：
- Feature Flag 删除/归档与快照
- Agent bootstrap 指引
- smoke test / API tests
- 配置修改审计

这样做的好处是，每一小段都能快速形成明确价值，而不是把所有事情堆在一个大版本里。

---

## 6. 我建议的实现优先顺序

如果按“投入产出比”排序，我建议实际开发顺序是：

1. 项目配置编辑 + Agent Token 重置  
2. Webhook 签名校验 + 分支过滤 + 幂等  
3. 部署超时 / 异常 running 兜底  
4. 健康看板  
5. 部署详情自动刷新与日志增强  
6. Feature Flag 删除/归档  
7. 测试与 smoke 脚本

原因很直接：
- 1 到 3 先解决“不能稳定用”的问题
- 4 到 5 再解决“出了问题不好看懂”的问题
- 6 到 7 最后补“长期维护成本”

---

## 7. v0.3 完成定义

满足以下条件时，可以认为 `v0.3` 基本成立：

- 能在面板里完成项目配置维护，不需要直接改数据库
- 能安全接 webhook，不会被错误请求或重复请求污染任务队列
- 部署任务不会长期卡死为 `running`
- 面板能区分部署失败、健康失败、Agent 离线三种常见问题
- 用户可以在 5 分钟内定位最近一次失败的大致原因
- 至少有一套最小 smoke 流程保证核心闭环可回归验证

---

## 8. 一句话结论

`v0.3` 最值得补的，不是“更多功能”，而是把 ShipSmith 从一个 **MVP 演示版**，推进成一个 **独立开发者真的能持续拿来管线上项目的自用控制台**。
