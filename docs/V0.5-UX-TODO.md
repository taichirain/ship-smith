# ShipSmith v0.5 开发任务清单

> 版本：v0.5 执行清单  
> 日期：2026-05-09  
> 关联文档：`docs/V0.5-UX-PLAN.md`

---

## 1. 使用方式

这份文档只做一件事：

**把 `v0.5` 的“极致易用性目标”拆成可逐项实现的任务。**

原则：
- 优先做真正影响首日体验和失败理解成本的能力
- 优先解决“用户不知道填什么、为什么失败、接下来该做什么”
- 避免把 LLM 做成大而泛的聊天入口
- 所有 LLM 能力都优先建立在结构化规则和已有上下文之上

建议节奏：
- 先做 `v0.5.0`
- 每做完一个小版本，就找一个“几乎不懂运维”的真实视角走查
- 如果某项能力不能明显降低接入失败率、部署失败率或排障焦虑，就降级优先级

## 2. v0.5.0

目标：先让新手能顺利接入，不被配置表单劝退。

### 2.1 项目接入向导

#### API
- [ ] 梳理“创建项目”最小必填字段
  建议至少覆盖：
  - project name
  - git repo
  - git branch
  - deploy workdir
  - compose file
  - compose service
  - health check url
- [ ] 为项目创建接口补充更细的字段级校验
- [ ] 增加项目配置预览接口或复用现有 schema 生成预览
- [ ] 明确哪些字段允许为空、哪些字段必须后续补齐

完成定义：
- API 可以支撑一个分步式创建流程，而不是只适合一次性提交完整表单

#### Web
- [ ] 将“新建项目”改成分步向导
- [ ] 每一步只展示当前阶段必需的信息
- [ ] 为关键字段增加示例值和简短说明
- [ ] 在最后一步展示完整配置摘要
- [ ] 支持复制或导出 `shipsmith.yaml` 预览内容
- [ ] 创建成功后直接跳转到项目接入下一步，而不是只回列表页

完成定义：
- 新用户可以在一个引导流程里完成项目创建，不需要先理解完整配置格式

### 2.2 配置解释层

#### API / Schema
- [ ] 为关键配置字段整理元信息
  建议包含：
  - label
  - description
  - example
  - placeholder
  - risk hint
- [ ] 评估是否将字段说明抽成前后端可共享配置

完成定义：
- 字段解释不再散落在页面硬编码里，后续可稳定复用

#### Web
- [ ] 在项目创建页和项目编辑页展示字段说明
- [ ] 对新手不熟悉的概念增加人话解释
  例如：
  - health check
  - compose service
  - deploy strategy
  - flags file
- [ ] 对容易填错的字段增加即时校验提示
- [ ] 对高风险字段增加推荐值或推荐填写方式

完成定义：
- 用户在录入配置时就能理解大部分字段，不需要频繁翻文档

### 2.3 首次使用体验

#### Web
- [ ] 首页空状态增加 onboarding 区块
- [ ] 明确展示最短路径
  例如：
  - 创建项目
  - 获取 Agent 启动信息
  - 跑环境预检
  - 首次部署
- [ ] 为空项目列表、空部署记录、空告警等页面补充下一步动作
- [ ] 尽量减少黑话，优先使用新手可理解的文案

完成定义：
- 第一次打开系统的用户，不会面对多个“空页面 + 不知道下一步做什么”

## 3. v0.5.1

目标：在正式部署前，把环境和配置问题尽量提前暴露。

### 3.1 Agent 环境预检

#### Agent
- [ ] 设计自检命令
  建议：`shipsmith-agent doctor` 或等价命令
- [ ] 检查基础依赖：
  - `git`
  - `docker`
  - `docker compose`
- [ ] 检查项目环境：
  - deploy workdir 是否存在
  - workdir 是否可读写
  - compose file 是否存在
  - env file 是否存在（如果配置了）
  - flags 文件目录是否可写
- [ ] 检查运行连通性：
  - health check url 是否可访问
  - 目标服务返回状态是否符合预期
- [ ] 输出结构化结果
  建议字段：
  - `status`
  - `category`
  - `check_name`
  - `summary`
  - `details`
  - `suggestion`

完成定义：
- Agent 可以稳定输出一份可读、可机读的预检结果

#### API
- [ ] 增加预检结果上报接口
  建议：`POST /api/v1/projects/{id}/preflight-results`
- [ ] 增加查询最近一次预检结果接口
  建议：`GET /api/v1/projects/{id}/preflight-results/latest`
- [ ] 预留预检历史存储能力，至少保留最近一次结果和时间

完成定义：
- 面板可以展示“最近一次预检是否通过，以及失败在哪”

#### DB
- [ ] 增加 preflight results 表或等价存储
- [ ] 记录：
  - project id
  - agent id
  - overall status
  - check results
  - created at

完成定义：
- 预检结果可被查询、展示、回看，而不是只打印在终端里

#### Web
- [ ] 项目详情页增加“环境预检”区块
- [ ] 展示总状态：passed / warning / failed
- [ ] 展示每项检查结果和建议动作
- [ ] 对失败项做更强视觉提示
- [ ] 如果项目从未预检，明确提示先跑预检再部署

完成定义：
- 用户在点部署之前，就能知道机器环境是否基本靠谱

### 3.2 常见问题修复建议

#### API / 规则层
- [ ] 定义高频错误分类规则
  建议首批覆盖：
  - git auth failed
  - repo not found
  - compose file missing
  - env file missing
  - docker permission denied
  - image build failed
  - container startup failed
  - health check 404
  - health check timeout
  - port already in use
- [ ] 为每种错误分类编写固定建议模板
- [ ] 在部署失败和预检失败时复用同一套分类与建议逻辑

完成定义：
- 常见错误至少能给出稳定、可重复的第一轮排查建议

#### Web
- [ ] 在部署详情页展示“建议先检查什么”
- [ ] 在预检结果页复用同样的建议卡片
- [ ] 明确保留原始错误，不要只展示建议

完成定义：
- 用户不离开页面，也能开始第一轮排障

## 4. v0.5.2

目标：失败后别让用户被日志吓跑，把 LLM 用在最值的地方。

### 4.1 部署失败人话总结

#### API / 服务层
- [ ] 为部署结果增加结构化失败摘要字段
  建议：
  - `failure_phase`
  - `error_code`
  - `error_summary`
  - `human_summary`
  - `suggested_checks`
- [ ] 在规则命中时优先使用规则层生成摘要
- [ ] 仅在规则层信息不足时，调用 LLM 补充说明
- [ ] 设计 LLM 输入边界
  至少控制：
  - 输入日志长度
  - 只传必要上下文
  - 不传敏感 token / secret
- [ ] 为 LLM 输出增加落地约束
  例如：
  - 1 段失败解释
  - 2 到 3 条建议
  - 不输出“我不确定但你可以试试很多事”这种泛化废话

完成定义：
- 失败总结即使不调用 LLM，也能依赖规则层提供基本可用结果
- 引入 LLM 后，输出质量明显更好但不会失控

#### Web
- [ ] 在部署详情页顶部增加“失败总结”卡片
- [ ] 摘要区优先展示：
  - 失败阶段
  - 人话解释
  - 建议检查项
- [ ] 原始日志仍然完整保留在下方
- [ ] 标记哪些内容来自规则判断、哪些来自 LLM 补充

完成定义：
- 用户先读摘要，再决定是否下钻日志，而不是一上来就面对整页日志

### 4.2 LLM 使用边界与开关

#### API / 配置
- [ ] 增加系统级 LLM 配置开关
- [ ] 支持关闭 LLM 后仍保留规则层失败总结
- [ ] 支持配置模型、超时和最大输入大小
- [ ] 记录 LLM 摘要生成是否成功，以及失败原因

完成定义：
- LLM 是增强项，不是核心链路单点依赖

#### Web
- [ ] 增加简单的 LLM 设置页或系统设置区块
- [ ] 明确提示 LLM 的用途仅限：
  - 失败解释
  - 配置说明补充
  - 排障建议增强
- [ ] 明确不是自动执行器，不会直接修改服务器

完成定义：
- 用户能理解系统为什么用了 LLM，也能理解它不会替自己做高风险决定

### 4.3 结构化 Runbook

#### DB
- [ ] 为项目增加 runbook 存储结构
  建议字段：
  - overview
  - release_notes
  - rollback_notes
  - common_issues
  - useful_links
  - owner

完成定义：
- Runbook 不只是一个大文本框，后续可按块展示和联动

#### API
- [ ] 增加项目 runbook 查询接口
- [ ] 增加项目 runbook 更新接口
- [ ] 新建项目时自动生成基础模板

完成定义：
- 每个项目都能带一个最小可用的运维说明，不需要手工从零写

#### Web
- [ ] 项目详情页增加 Runbook 区块
- [ ] 支持结构化编辑
- [ ] 部署失败时联动展示“常见故障”和“回滚说明”
- [ ] 若 runbook 为空，展示引导模板而不是空白编辑框

完成定义：
- 用户打开项目页就能看到操作说明和常见问题，不需要跳到外部文档

## 5. 横向任务

目标：避免这轮只做了表层体验，却没有稳定性和验收保障。

### 5.1 文案与术语统一

#### Web / 产品
- [ ] 统一术语
  建议优先使用：
  - “环境预检” 而不是过多技术黑话
  - “失败总结” 而不是“AI 分析”
  - “建议检查项” 而不是“根因推理”
- [ ] 检查所有空状态、错误提示、按钮文案是否适合新手理解

完成定义：
- 主要页面术语统一，不会同一概念出现多种叫法

### 5.2 测试

#### API Test
- [ ] 项目向导创建流程测试
- [ ] 预检结果上报与查询测试
- [ ] 错误分类和建议模板测试
- [ ] 失败摘要字段返回测试
- [ ] Runbook CRUD 测试
- [ ] LLM 开关关闭时的降级测试

完成定义：
- v0.5 关键接口具备最小回归保护

#### Agent Test
- [ ] doctor 命令输出结构测试
- [ ] 常见失败场景模拟测试
- [ ] 预检结果序列化测试

完成定义：
- 预检能力不会因为后续修改而悄悄失效

#### Web Test / Smoke
- [ ] 首次使用路径 smoke
  例如：
  - 空系统进入
  - 创建项目
  - 查看接入说明
  - 看到预检引导
- [ ] 部署失败后的失败总结展示 smoke
- [ ] Runbook 联动展示 smoke

完成定义：
- 可以从“新手首次进入”到“看到失败总结”走通一条完整链路

## 6. 不在 v0.5 做的事

为了控制边界，这阶段明确不做：
- [ ] 自然语言直接执行部署、回滚、改配置
- [ ] AI 自动修复服务器问题
- [ ] 通用聊天式 Copilot 面板
- [ ] 大而全模板市场
- [ ] 多步智能编排工作流

完成定义：
- `v0.5` 的 AI 仍然是解释层，不演变成高风险自动驾驶系统

---

## 7. 一句话执行结论

`v0.5` 的核心不是让 ShipSmith “更聪明”，而是让用户：
- 更容易接进来
- 更早发现问题
- 更看得懂失败
- 更不容易误操作

如果某项功能做不到这四点之一，就不该放在这轮的高优先级里。
