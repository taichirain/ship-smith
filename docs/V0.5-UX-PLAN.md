# ShipSmith v0.5 规划：把易用性做到极致

> 版本：v0.5 规划草案  
> 日期：2026-05-09  
> 目标：在 v0.4 已具备轻量运维工作台雏形的基础上，进一步降低接入门槛、排障门槛和使用焦虑，让不懂运维的人也敢用

---

## 1. 这次要解决的问题

`v0.4` 之后，ShipSmith 会更像一个真正可日常打开的轻量运维工具：
- 有全局首页
- 有通知和告警
- 有项目时间线
- 有更顺手的巡检和排障入口

这已经能服务一批“懂一点运维的独立开发者”。

但如果继续往前走，ShipSmith 很可能会遇到第二类用户：
- 会写一点代码，甚至主要靠 LLM 做产品
- 能理解“部署”这个概念，但不理解 Linux / Docker / 健康检查细节
- 遇到失败时，不知道该先看配置、权限、网络还是容器日志

这类用户不是要更强的运维能力，而是要更低的理解成本。

所以 `v0.5` 的重点不应该是继续横向扩功能，而应该做三件事：
- **让接入更像填写向导，而不是配系统**
- **让错误更像人话提示，而不是命令行残片**
- **让 LLM 成为解释层和辅助手，而不是黑盒自动驾驶**

一句话定义 `v0.5`：

**把 ShipSmith 从“轻量运维工具”，推进成“对新手极其友好的部署控制台”。**

---

## 2. v0.5 的产品判断

对这阶段来说，最重要的不是“AI 味更浓”，而是“第一次使用就不慌”。

对于新手，真正高频且最痛的点通常是这些：
- 不知道新建项目时每个字段该填什么
- 不知道服务器环境是否满足运行前提
- 部署失败后只能看到一堆日志，不知道该从哪里开始排查
- 不理解健康检查、compose 文件、env、权限这些概念之间的关系
- 一段时间后连自己都忘了这个项目该怎么发版、怎么回滚

所以 `v0.5` 不该优先做这些：
- AI 自动修服务器
- 自然语言直接执行高风险运维动作
- 泛化聊天助手
- 模板市场、工作流编排平台
- 更复杂的发布策略

`v0.5` 应该优先做的是：
- **引导式接入**
- **环境预检**
- **失败解释**
- **安全默认值**
- **知识留存**

---

## 3. v0.5 核心方向

按价值分为三档：`必须做 / 很值 / 可以后放`。

## 3.1 必须做

### A. 项目接入向导

目标：让用户通过表单和引导完成项目接入，而不是先理解配置格式。

建议补齐：
- 新建项目改成分步向导
- 按步骤采集最少必填信息：
  - 仓库地址
  - 分支
  - 部署目录
  - compose 文件路径
  - 主服务名
  - 健康检查地址
- 每一步都提供简短解释和示例
- 自动生成配置预览
- 允许用户在最后一步复制或导出 `shipsmith.yaml`

为什么重要：
- 新手不是怕填信息，而是怕填错后不知道哪里错
- 先把“配置系统”转换成“回答问题”，接入阻力会明显下降

完成定义：
- 一个从未接入过项目的用户，基本可以只靠页面向导完成首个项目创建
- 即使用户不理解 `shipsmith.yaml`，也不会阻塞使用

### B. Agent 环境预检

目标：在正式部署前，先判断机器是否具备最基本的可运行条件。

建议补齐：
- 提供 Agent 自检能力
- 至少检查：
  - `git` 是否可用
  - `docker` / `docker compose` 是否可用
  - 工作目录是否存在、是否可读写
  - compose 文件是否存在
  - health check url 是否可访问
  - env file 是否存在
  - flags 文件目录是否可写
- 自检结果用结构化状态返回：
  - passed
  - warning
  - failed
- 每个失败项都给出下一步建议

为什么重要：
- 新手最怕“点了部署才知道环境根本不对”
- 预检的价值往往高于多加一堆部署按钮

完成定义：
- 用户在首次部署前，就能知道是缺依赖、路径错、权限错还是健康检查配置错
- 大多数接入失败都能在预检阶段被提前暴露

### C. 部署失败人话总结

目标：失败不再只是日志事实，而是带有解释和排查建议。

建议补齐：
- 为部署结果增加结构化失败摘要
- 至少输出：
  - 失败发生在哪个阶段
  - 系统原始错误摘要
  - 面向人的简要解释
  - 优先排查的 2 到 3 个方向
- 对常见失败模式做规则层归类：
  - git 拉取失败
  - 仓库权限失败
  - compose 文件缺失
  - 镜像构建失败
  - 容器启动失败
  - 健康检查失败
  - 端口占用
  - 权限不足
- 在规则归类不足时，再让 LLM 基于结构化上下文生成补充说明

为什么重要：
- 这是 LLM 最值得切入的点：解释，而不是代替用户执行
- 新手通常不是看不懂全部日志，而是不知道“先看哪一行”

完成定义：
- 一个失败部署打开详情页后，用户能先读摘要，再决定是否深入原始日志
- 同类错误的解释风格保持稳定，不要忽长忽短、忽准忽玄

### D. 安全默认值与防误操作

目标：默认行为要保守，让新手更不容易把自己坑到。

建议补齐：
- 新项目默认关闭 webhook 自动部署
- 默认必须通过健康检查才算部署成功
- 默认突出“最近一次成功部署”和回滚入口
- 对高风险操作增加明确确认：
  - rotate token
  - rollback
  - archive flag
  - 重新部署生产项目
- 对关键设置给出“推荐值”而不是让用户空着猜

为什么重要：
- 新手的核心问题往往不是能力不够，而是边界感不够
- 保守默认值能显著减少第一次上线时的事故概率

完成定义：
- 即使用户对运维理解有限，也不容易因为一个错误默认值直接把服务打挂

### E. 结构化 Runbook

目标：让项目知识跟着项目走，而不是散落在人脑和聊天记录里。

建议补齐：
- 每个项目支持结构化运行手册
- 建议字段：
  - 项目说明
  - 发布注意事项
  - 常见故障
  - 回滚说明
  - 常用地址
  - 负责人或维护人
- 新建项目时自动生成一个基础模板
- 当部署连续失败时，可在详情页联动展示相关 runbook 内容

为什么重要：
- 对新手和未来的自己，这类“运维备注”比复杂团队权限更实用
- 这能把 ShipSmith 从操作面板进一步推进到工作台

完成定义：
- 用户打开项目页，不需要切回 Notion、飞书或终端历史去找基本操作说明

## 3.2 很值，建议紧接着做

### F. 配置解释层

目标：让每个配置项不只是一行字段，而是一个可理解的概念。

建议补齐：
- 在项目配置页增加“这项配置是做什么的”解释
- 对关键字段增加示例值
- 对容易填错的字段给出输入前校验和错误提示
- 对新手不熟悉的概念补充一句人话说明：
  - 健康检查
  - compose service
  - flags 文件路径
  - deploy strategy

为什么值：
- 很多错误不是运行期才出现，而是录入配置时就已经埋下

完成定义：
- 用户在配置页里就能理解大部分字段含义，不需要再翻文档

### G. 常见问题修复建议

目标：把排障建议前置，不让用户每次都从零搜索。

建议补齐：
- 为高频错误附带推荐检查动作
- 例如：
  - 健康检查 404：检查 URL 路径和服务监听端口
  - 权限不足：检查 Agent 用户和 Docker 组权限
  - compose 文件不存在：检查 `deploy.workdir` 和 `compose.file`
  - env 文件缺失：检查 `.env` 是否存在或路径是否正确
- 建议以“先做什么、再做什么”的顺序呈现
- 保留原始错误，不要只显示建议

为什么值：
- 对新手来说，第一步排障指引比完整原理更重要

完成定义：
- 至少覆盖 10 到 15 类高频错误
- 用户无需离开页面搜索，就能开始第一轮排查

### H. 首次使用体验优化

目标：让第一次打开系统的人，不会被空白界面和陌生术语劝退。

建议补齐：
- 新安装后首页增加 onboarding 引导
- 明确系统最短路径：
  - 创建项目
  - 安装 Agent
  - 跑预检
  - 首次部署
- 空状态页面给出下一步动作，不只是空列表
- 演示文案尽量避免运维黑话

为什么值：
- 产品能否被新手真正开始用，很多时候就取决于前 10 分钟体验

完成定义：
- 首次使用者在没有额外讲解的前提下，也能理解系统基本工作流

## 3.3 可以后放

### I. LLM 侧边助手

可以考虑，但不急着做：
- 基于当前项目上下文回答“这次为什么失败”
- 解释某项配置是什么意思
- 把 runbook 内容转成更自然的问答形式

为什么后放：
- 如果前面的结构化数据、预检和失败摘要没做好，聊天助手只会掩盖产品设计问题

### J. 配置模板与场景模板

可以考虑，但不急着做：
- Next.js + Docker Compose 模板
- FastAPI + PostgreSQL 模板
- Node 服务 + 健康检查模板

为什么后放：
- 模板当然有用，但如果配置解释层和接入向导还不成熟，模板只会暂时绕开问题，不是真正解决问题

---

## 4. LLM 在 v0.5 里应该扮演什么角色

这里建议保持非常克制。

LLM 更适合做：
- 日志和失败原因解释
- 配置项的人话说明
- 排障建议生成
- runbook 辅助阅读

LLM 不适合在这个阶段做：
- 自动执行高风险命令
- 自动修改服务器配置
- 自动决定是否继续部署
- 成为主要交互入口

产品原则建议定成一句话：

**LLM 负责解释和建议，人类负责确认和执行。**

这样做的好处：
- 能明显降低新手理解门槛
- 不会把核心体验建立在“AI 猜得准不准”上
- 出错时责任边界更清晰

---

## 5. 推荐的 v0.5 版本切法

如果你希望这阶段依然做得稳，我建议拆成三个小版本。

### v0.5.0

聚焦“先让新手能接进来”：
- 项目接入向导
- 配置解释层
- 空状态和 onboarding 优化

### v0.5.1

聚焦“先让系统在部署前把坑说清楚”：
- Agent 环境预检
- 预检结果展示
- 常见错误修复建议

### v0.5.2

聚焦“失败后别把人吓跑”：
- 部署失败人话总结
- 规则归类 + LLM 补充解释
- 结构化 Runbook

这样切的好处是：
- `v0.5.0` 先提升接入成功率
- `v0.5.1` 再降低首次部署失败率
- `v0.5.2` 最后处理失败后的理解成本

整个节奏会比“先上 AI 助手”更扎实。

---

## 6. 一句话优先级结论

如果 `v0.5` 只能押一个方向，我建议押这个：

**不要先做聊天式 AI，要先做向导式接入、预检式兜底、解释式排障。**

因为对 ShipSmith 来说，真正的易用性，不是“看起来更聪明”，而是“用户更少犯错、更少害怕、更少卡住”。
