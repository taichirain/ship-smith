# ShipSmith v0.4 开发任务清单

> 版本：v0.4 执行清单  
> 日期：2026-05-08  
> 关联文档：`docs/V0.4-OPS-PLAN.md`

---

## 1. 使用方式

这份文档只做一件事：

**把 `v0.4` 的“好用性目标”拆成可逐项实现的任务。**

原则：
- 优先做高频、小而值的能力
- 避免把任务拆成抽象口号
- 每项都尽量有明确完成定义

建议节奏：
- 先做 `v0.4.0`
- 每完成一个小版本，就做一次真实自用走查
- 如果某个功能不能减少刷新次数、点击次数或排障时间，就降级优先级

## 2. v0.4.0

目标：先解决“看不见全局问题”的缺口。

### 2.1 全局运维首页

#### API
- [ ] 增加 dashboard summary 接口
  建议：`GET /api/v1/dashboard/summary`
- [ ] 返回全局摘要：
  - 项目总数
  - healthy 数量
  - degraded / unhealthy 数量
  - offline 数量
  - 近 24 小时 deployment success / failed 数量
- [ ] 返回异常项目列表
  规则至少覆盖：
  - agent offline
  - app health 非 healthy
  - 最近一次 deployment failed
  - 超过阈值未心跳
- [ ] 返回最近变更流
  至少聚合：
  - deployment
  - rollback
  - flag audit
  - webhook delivery

完成定义：
- 一个接口或一组小接口足以支撑首页，不需要前端拼太多二次逻辑

#### DB / 查询层
- [ ] 定义 offline 判定阈值
  建议先固定，如 `agent_last_seen_at > 2 * heartbeat interval`
- [ ] 梳理最近变更流的数据来源
- [ ] 如现有查询成本过高，增加必要索引

完成定义：
- 首页数据拉取不会因为项目数增加而明显变慢

#### Web
- [ ] 新增首页 dashboard 页面
- [ ] 顶部显示摘要卡片
- [ ] 中间显示异常项目列表
- [ ] 下方显示最近变更流
- [ ] 异常项目项支持直接跳转到项目详情或最近失败 deployment
- [ ] 页面支持手动刷新

完成定义：
- 用户打开首页 5 秒内能知道今天先该处理什么

### 2.2 项目列表升级

#### API
- [ ] `GET /api/v1/projects` 增加筛选参数
  建议：
  - `health_status`
  - `q`
  - `sort_by`
  - `sort_order`
- [ ] 项目列表返回更多摘要字段
  建议追加：
  - current_commit_hash
  - last_deployment_status
  - last_deployment_at

完成定义：
- 列表接口可直接支撑工作台式巡检页面

#### Web
- [ ] 项目列表增加搜索框
- [ ] 增加状态筛选 tabs / select
- [ ] 增加排序选项
  例如：
  - 最近失败优先
  - 最近部署优先
  - 最久未心跳优先
- [ ] 列表卡片补充最近部署和最近心跳摘要

完成定义：
- 项目数量到 20 到 50 时，列表页仍可直接用来巡检

### 2.3 项目时间线

#### API
- [ ] 增加项目 timeline 接口
  建议：`GET /api/v1/projects/{id}/timeline`
- [ ] 时间线聚合以下事件：
  - deployment queued / success / failed
  - rollback
  - flag create / update / archive / unarchive
  - project config update
  - webhook accepted / ignored
  - agent offline / recovered
- [ ] 统一时间线事件结构
  建议字段：
  - `type`
  - `occurred_at`
  - `title`
  - `summary`
  - `actor`
  - `metadata`

完成定义：
- 时间线接口足够稳定，后续更多事件类型也能继续追加

#### DB
- [ ] 评估 project config update 是否需要新增审计表
- [ ] 如需补审计，增加 migration 和 model

完成定义：
- “配置谁改了什么”不再丢失

#### Web
- [ ] 项目详情页新增 timeline 区块
- [ ] 支持按事件类型过滤
- [ ] 支持点击 deployment 事件跳转详情
- [ ] 支持对重要事件使用更强视觉区分
  例如：failed、rollback、archived flag

完成定义：
- 打开项目页后，不需要来回扫多个区块才能理解最近变更

## 3. v0.4.1

目标：让问题主动找你，并且别太吵。

### 3.1 通知系统基础

#### DB
- [ ] 增加 notification channels 表
- [ ] 增加 project notification settings 表
- [ ] 增加 notification deliveries 或发送记录表

完成定义：
- 可以区分“发到哪里”“哪个项目启用哪些事件”“实际发没发成功”

#### API
- [ ] 增加通知渠道 CRUD
  建议先支持：
  - generic webhook
  - Feishu bot webhook
  - Slack webhook
- [ ] 增加项目级通知配置接口
- [ ] 支持事件开关：
  - deployment success
  - deployment failed
  - agent offline
  - health degraded / unhealthy
  - health recovered
- [ ] 增加测试发送接口

完成定义：
- 用户可以配置一个渠道并验证消息格式确实可用

#### 发送逻辑
- [ ] 在 deployment finish 时触发 success / failed 通知
- [ ] 在 heartbeat 状态变化时触发 health / recovery 通知
- [ ] 在 agent 连续离线达到阈值时触发 offline 通知

完成定义：
- 关键运维事件可以自动发送，不靠人工刷新页面

### 3.2 通知降噪

#### API / 任务逻辑
- [ ] 增加冷却窗口
  例如同一项目同类异常 10 分钟内不重复提醒
- [ ] 支持恢复通知
- [ ] 支持简单去重键
  例如：`project_id + event_type + fingerprint`

完成定义：
- 不会因为某个服务抖动就把渠道刷爆

#### Web
- [ ] 通知配置页增加：
  - 开关
  - 冷却时间
  - 是否发送恢复通知
- [ ] 在页面上展示最近测试结果或最近发送状态

完成定义：
- 用户能判断“没收到通知”是没触发，还是发送失败

### 3.3 面板内 recent alerts

#### DB / API
- [ ] 增加 alerts 表
- [ ] 告警状态至少支持：
  - open
  - acknowledged
  - resolved
- [ ] 告警来源先接：
  - agent offline
  - deployment failed
  - health unhealthy
- [ ] 增加 alerts 列表接口
- [ ] 增加 acknowledge / resolve 接口

完成定义：
- 异常不仅发消息，也能在系统里被持续跟踪

#### Web
- [ ] 首页增加 recent alerts 区块
- [ ] 支持 acknowledge
- [ ] 支持按状态过滤

完成定义：
- 用户能分清哪些问题还没处理，哪些只是已知问题

## 4. v0.4.2

目标：让处理问题更顺手。

### 4.1 快捷运维动作

#### API
- [ ] 增加 `retry deployment` 接口
  建议：
  - 传入历史 deployment id
  - 复用原始 commit / trigger metadata
- [ ] 增加“回滚到最近成功版本”快捷接口
  或在现有 rollback 能力上封装快捷查询
- [ ] 增加 deployment 日志下载接口
  格式可先用纯文本

完成定义：
- 常用运维动作不需要前端手工拼数据

#### Web
- [ ] 项目详情页增加 retry 最新失败部署按钮
- [ ] 项目详情页增加 rollback to last success 按钮
- [ ] deployment 详情页增加下载日志按钮
- [ ] 为复制类动作统一做 copy feedback

完成定义：
- 常见处理动作控制在 1 到 2 步

### 4.2 复制与跳转类小工具

#### Web
- [ ] 项目页统一整理快捷信息区
- [ ] 一键复制：
  - webhook endpoint
  - webhook secret
  - agent id
  - 当前 commit
  - 最近错误码
- [ ] 一键打开：
  - health url
  - repo url
- [ ] 一键跳转最近失败 deployment

完成定义：
- 减少切页面、选中文本、手工拼 URL 的时间

### 4.3 Runbook / 备注 / 常用地址

#### DB
- [ ] 为 projects 增加运维补充字段，或设计独立 project_notes 表
  建议字段：
  - notes
  - release_notes_hint
  - troubleshooting_hint
  - admin_url
  - metrics_url
  - logs_url
  - ssh_hint

完成定义：
- 项目可以承载运维知识，而不只是机器配置

#### API
- [ ] 增加项目运维信息读写接口

完成定义：
- 前端可以单独维护 runbook 信息，不污染核心部署字段

#### Web
- [ ] 项目详情页增加 Runbook 区块
- [ ] 支持编辑备注
- [ ] 支持展示常用入口链接

完成定义：
- 新人或未来的自己，打开项目页就能知道怎么处理

## 5. v0.4.3

目标：让状态判断更从容，不只看瞬时点。

### 5.1 轻量健康趋势

#### API
- [ ] 增加项目健康历史接口
  建议：`GET /api/v1/projects/{id}/health-history`
- [ ] 支持时间范围：
  - 24h
  - 7d
- [ ] 返回最小必要数据：
  - timestamp
  - health_status
  - response_ms
  - heartbeat_present
- [ ] 返回 deployment markers

完成定义：
- 前端可以画最基本的趋势，不需要复杂聚合

#### Web
- [ ] 项目页增加轻量历史图
- [ ] 支持 24h / 7d 切换
- [ ] 在图上标出 deployment 点位

完成定义：
- 用户能看出异常是偶发抖动还是持续恶化

### 5.2 Agent 版本信息

#### Agent
- [ ] heartbeat 增加 agent version 字段

#### API
- [ ] 项目状态接口返回 agent version
- [ ] 如可能，增加“版本是否过旧”的判断逻辑

#### Web
- [ ] 项目页显示 agent version
- [ ] 首页或列表页可标记落后版本

完成定义：
- 多台机器时，用户能快速发现版本不一致问题

### 5.3 数据保留与清理

#### API / 后台任务
- [ ] 定义 heartbeat retention policy
- [ ] 定义 deployment logs retention policy
- [ ] 定义 webhook payload retention policy
- [ ] 提供清理脚本或管理命令

完成定义：
- 系统长期运行时不会无限堆历史数据

## 6. 横切整理项

### 6.1 统一“异常”语义
- [ ] 收敛 offline / degraded / unhealthy / failed 的判定标准
- [ ] 首页、项目页、通知、alerts 使用同一套语义

完成定义：
- 用户不会在不同页面看到同一状态被不同方式解释

### 6.2 文案与信息架构
- [ ] 收敛页面上的状态文案
- [ ] 优先使用运维视角命名，而不是内部实现视角
  例如：
  - `Agent Offline`
  - `Health Check Failed`
  - `Deploy Failed`

完成定义：
- 用户扫一眼就懂，不需要理解内部状态机

### 6.3 自用走查
- [ ] 用 3 到 5 个真实项目做一次日常巡检模拟
- [ ] 用一次失败部署做全链路走查
- [ ] 用一次 agent 离线做通知和告警走查

完成定义：
- 至少有一轮真实场景验证，而不是只看功能是否存在

## 7. 建议开发顺序

建议按下面顺序推进：

1. dashboard 首页
2. 项目时间线
3. 项目列表筛选与排序
4. 通知渠道与测试发送
5. deployment / health / offline 事件通知
6. alerts 列表与 acknowledge
7. retry / rollback / 下载日志
8. runbook / 备注 / 常用地址
9. 健康趋势
10. agent version
11. retention policy

原因：
- 前 3 项先解决“看见问题”
- 4 到 6 解决“问题主动来找你”
- 7 到 8 解决“处理问题更顺手”
- 9 到 11 解决“长期运维更稳定”

## 9. 一句话执行建议

`v0.4` 最重要的不是增加“更高级的部署能力”，而是把 ShipSmith 做成一个：

**早上打开就知道哪有问题，出事后第一时间收到提醒，点两下就能继续处理的轻量运维工作台。**
