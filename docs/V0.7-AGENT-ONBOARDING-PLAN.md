# ShipSmith v0.7 规划：Agent 接入体验升级

> 版本：v0.7 规划草案
> 日期：2026-05-09
> 目标：在不改变 Agent 架构的前提下，显著降低首次接入门槛，并把安装过程产品化

---

## 1. 这次要解决的问题

`v0.6` 之后，ShipSmith 的部署主线会更清晰：
- 继续坚持 Agent 架构
- 支持单项目多机部署
- 不走 SSH 直接部署

但还有一个现实问题没有真正解决：

**很多用户不是反对 Agent，而是嫌 Agent 安装过程麻烦。**

常见阻力通常不是“我不接受常驻进程”，而是：
- 不知道先执行哪条命令
- 不想手动填一堆环境变量
- 不确定 Agent 启动后算不算安装成功
- 机器环境有问题时，不知道卡在哪

所以 `v0.7` 的重点不应该是增加新的部署模型，而应该是：

**把 Agent 接入从“文档步骤”变成“产品能力”。**

---

## 2. 版本结论

`v0.7` 聚焦两件事：

1. 一键生成安装命令
2. SSH 辅助安装 Agent

但这两件事优先级不同。

### 2.1 第一优先级

先做：

**一键安装命令**

原因：
- 实现复杂度更低
- 架构风险更低
- 覆盖用户更多
- 足以解决大部分首次接入阻力

### 2.2 第二优先级

再做：

**SSH 辅助安装 Agent**

原因：
- 它解决的是更深一层的“我连命令都不想自己执行”
- 价值存在，但不应成为产品主路径
- 一旦做重，很容易滑向远程运维面板

---

## 3. 产品原则

`v0.7` 仍然坚持下面这些原则：

- Core 不负责 SSH 直接部署项目
- Agent 仍然是唯一正式部署执行面
- SSH 只允许用于“首次接入辅助安装”
- 不保存长期 SSH 管理关系
- 不提供通用远程执行能力

一句话：

**v0.7` 做的是“更容易把 Agent 装上去”，不是“改成 SSH 运维产品”。**

---

## 4. 一键安装命令

### 4.1 用户价值

这项能力的目标非常直接：

**让用户在项目创建后，只需要去服务器执行一条命令，就能把 Agent 装好并连回 Core。**

它主要解决：
- 命令太多
- 步骤太散
- 环境变量太难抄
- 安装成功没有反馈

### 4.2 最小产品形态

建议页面直接提供两种接入方式：

- 快速安装命令
- 手动安装步骤

其中“快速安装命令”是主路径，“手动安装步骤”是排错 fallback。

建议的最小体验是：

1. 用户创建项目
2. 页面显示一条可复制的安装命令
3. 用户在目标服务器执行
4. Agent 自动完成安装并启动
5. 页面自动轮询并提示 `Agent online`

### 4.3 推荐边界

一键安装命令负责：
- 下载 Agent
- 写入必要配置
- 安装为 systemd 服务
- 启动服务
- 输出结果与下一步提示

一键安装命令不负责：
- 自动修复复杂环境问题
- 远程升级所有 Agent
- 替代部署逻辑
- 通用服务器初始化

### 4.4 为什么值得优先做

这是一个典型的高收益、低架构扰动能力。

它不会破坏现在的控制模型，却能明显改善：
- 首次试用体验
- 新项目接入速度
- 文档依赖程度
- 安装失败后的可判断性

对多数用户来说，这已经足够好了。

---

## 5. SSH 辅助安装 Agent

### 5.1 它真正要解决的问题

这项能力不是给长期使用的，而是给首次接入时这类用户：

- 我有服务器
- 我接受装 Agent
- 但我不想自己手动执行安装命令

所以它的定位必须非常明确：

**SSH 只用来远程安装 Agent，不用来长期管理项目部署。**

### 5.2 最小产品形态

建议流程：

1. 用户在项目页面点击“通过 SSH 安装 Agent”
2. 填写：
   - host
   - port
   - username
   - password 或 private key
3. Core 发起一次临时 SSH 会话
4. 远端执行 Agent 安装脚本
5. 安装成功后启动 Agent
6. Core 看到 Agent 回连
7. SSH 会话结束，流程终止

### 5.3 明确边界

`v0.7` 版本下，SSH 辅助安装只支持：
- Linux
- systemd
- 单机一次性安装
- 直连主机

不支持：
- SSH 直接部署项目
- 批量多机 SSH 安装
- jump host
- 长期保存 SSH 凭据
- 面板内终端
- 远程文件浏览
- 通用命令执行

### 5.4 为什么不能做重

如果这条线放开，很容易演变成另一类产品：
- 服务器资产管理
- 批量远程执行
- 远程终端
- 权限与审计
- 多主机编排

那会把 ShipSmith 从“部署控制面”拉向“运维面板”，产品焦点会明显漂移。

所以 SSH 相关能力必须被严格约束在“安装辅助层”。

---

## 6. 两者的关系

这两项能力不是并列主线，而是主从关系。

建议路径是：

- 主路径：一键安装命令
- 增强路径：SSH 辅助安装

因为真正可规模化、可维护、可解释的能力，还是一键安装命令。

SSH 辅助安装更像一个“帮用户少走一步”的增强器，而不是产品基础能力。

---

## 7. 页面与交互方向

### 7.1 项目创建成功后的接入页

建议把“项目创建成功”后的下一步做成专门页面，而不是只弹一次 token。

这个页面至少应展示：
- Agent token
- Core URL
- 快速安装命令
- 手动安装步骤入口
- Agent 在线状态
- 常见失败提示

### 7.2 SSH 辅助安装入口

SSH 安装入口不应放在最显眼的主操作位。

更合适的呈现方式是：
- 作为“高级接入方式”
- 或者“我不想手动执行命令”的辅助入口

这样能避免给新用户造成错误心智：

“ShipSmith 的标准用法是 SSH 管服务器。”

---

## 8. 技术影响范围

### 8.1 Core API

需要新增或补强：
- 安装命令生成接口
- Agent 接入状态查询接口
- SSH 辅助安装任务接口
- SSH 安装过程日志查询接口

### 8.2 Web

需要补齐：
- 接入引导页
- 一键安装命令展示与复制
- Agent 在线状态轮询
- SSH 安装表单
- SSH 安装进度与失败反馈

### 8.3 Agent / 安装包

需要补齐：
- 更稳定的安装脚本
- 更清晰的安装输出
- 更标准的 systemd 集成
- 安装后自检与回连提示

---

## 9. 风险判断

### 9.1 一键安装命令的风险

主要风险相对可控：
- 安装脚本兼容性
- systemd 差异
- 依赖缺失时的提示质量

这些都属于可以通过约束支持范围解决的问题。

### 9.2 SSH 辅助安装的风险

主要风险更高：
- SSH 凭据处理
- 认证失败和权限失败
- sudo 场景复杂
- 网络超时和远端环境差异
- 用户误以为后续部署也走 SSH

所以这项能力即使做，也必须明确是“受限辅助功能”。

---

## 10. 版本建议

建议把 `v0.7` 拆成两步：

### `v0.7.0`

先做：
- 一键安装命令
- 接入引导页
- Agent 在线状态反馈
- 手动安装 fallback

### `v0.7.1`

再评估是否增加：
- SSH 辅助安装 Agent

前提是你已经观察到真实用户信号，例如：
- 用户确实频繁卡在手动执行安装命令
- 一键命令仍不能覆盖主要接入障碍
- 用户要的是“帮我装 Agent”，不是“以后都靠 SSH 管机器”

---

## 11. 最终建议

`v0.7` 最值得做的，不是增加一种新的部署模型，而是把 Agent 接入体验做成产品能力。

所以建议的版本主线是：

- `v0.6`：多机 Agent 部署
- `v0.7`：Agent 接入体验升级

其中：
- 一键安装命令应作为主能力
- SSH 辅助安装应作为受限增强能力

如果 `v0.7` 做得好，用户会感受到的是：

**我并不需要理解太多运维细节，也能把 Agent 接上来。**

而不是：

**这个产品终于也能像传统面板一样 SSH 连服务器了。**
