# ShipSmith v0.6 规划：部署能力边界与多机最小方案

> 版本：v0.6 规划草案
> 日期：2026-05-09
> 目标：在不破坏 Agent 架构的前提下，明确部署能力边界，并补齐小团队可用的多机部署能力

---

## 1. 这次要回答的问题

`v0.5` 基本完成后，部署能力有两个自然延伸方向：

1. 要不要增加 SSH 部署方式
2. 要不要支持扩容后的多服务器部署

这两个方向都和“部署更多机器”有关，但它们的产品意义和实现代价完全不同。

这份文档的目标不是展开完整技术设计，而是先把范围边界定清楚。

---

## 2. 结论

### 2.1 SSH 部署方式

`v0.6` 不做。

保留当前原则：
- Core 不主动 SSH 到业务机
- 统一由 Agent 轮询 Core 领取任务
- 所有部署、日志、心跳、状态都走同一条控制链路

### 2.2 扩容后的多机部署

`v0.6` 建议做，但只做最小可用版本。

目标不是做编排平台，而是支持这类真实场景：
- 一个项目最开始只有 1 台服务器
- 后来增加到 2 到 5 台服务器
- 仍然使用 Git + Docker Compose
- 用户希望继续在同一个项目里发版，而不是拆成多个项目手工操作

---

## 3. 为什么不做 SSH

SSH 不是“多一种接入方式”这么简单，它会直接打破当前产品的控制模型。

当前 ShipSmith 的核心前提是：
- Agent 在目标机上执行命令
- Core 只负责发任务、收日志、记状态
- 不要求目标机开放 SSH 入站
- 不要求 Core 保存服务器登录凭据

如果增加 SSH，马上会引入额外复杂度：
- SSH 私钥或密码托管
- 跳板机、端口、网络连通性处理
- 远程命令执行权限和审计
- 日志采集模型与 Agent 模式不一致
- 重试、超时、断线恢复逻辑变成两套
- 用户需要理解“这个项目到底走 Agent 还是走 SSH”

对目标用户来说，这些复杂度并不会明显提升首要价值。

更关键的是，SSH 模式会削弱产品现在最清晰的定位：

**ShipSmith 不是远程登录工具，而是 Agent 驱动的轻量部署控制面。**

---

## 4. 为什么要做多机

多机部署更符合当前用户的自然成长路径。

一个刚起步的团队通常不是直接上 Kubernetes，而是按这个顺序演进：
- 第 1 阶段：1 台服务器
- 第 2 阶段：增加第 2 台应用机
- 第 3 阶段：前面挂一个 LB，后面跑 2 到 5 台应用机

如果 ShipSmith 只能稳定服务“永远单机”的场景，用户一旦扩容就会开始绕开它：
- 手工登录每台机器执行部署
- 把同一服务拆成多个项目分别点部署
- 外部脚本绕过控制面

这样产品会在用户刚开始长大的时候失去价值。

所以更合理的路线不是增加 SSH，而是把当前 Agent 模型从“单机项目”扩展到“多 Agent 项目”。

---

## 5. v0.6 的范围定义

### 5.1 要做什么

`v0.6` 只做下面这件事：

**一个项目可以绑定多台 Agent，并支持一次部署按策略下发到这些 Agent。**

支持的最小能力：
- 一个项目绑定多台服务器
- 每台服务器运行一个 Agent
- 用户可以看到每台机器的部署结果
- 支持两种发布方式：
  - `all-at-once`：同时发到所有机器
  - `rolling`：按顺序逐台发

### 5.2 明确不做什么

`v0.6` 不做：
- SSH 部署
- 自动扩缩容
- 负载均衡器联动摘流/加流
- 蓝绿发布
- 金丝雀发布
- 百分比灰度
- 跨机房或多地域编排
- 按批次暂停/继续
- 自动失败回滚所有机器

一句话：

**v0.6 做的是“多机部署记录与执行”，不是“完整发布编排系统”。**

---

## 6. 产品形态

### 6.1 项目模型

从：
- 一个项目绑定一个 `agent_id`

变成：
- 一个项目绑定多个部署目标
- 每个部署目标对应一台机器上的 Agent

建议新增“部署目标”概念，而不是直接把 Agent 平铺到项目上。

原因：
- 后面可以保留目标级元数据
- 可以区分“这是同一个项目下的第几台机器”
- 以后如果要支持批次、权重、角色，会更容易扩展

建议目标字段：
- `id`
- `project_id`
- `agent_id`
- `name`
- `role`，如 `app`
- `enabled`
- `order_index`，用于 rolling 顺序
- `last_seen_at`

### 6.2 部署模型

从：
- 一条 deployment 记录代表一次项目部署

变成：
- 一条 project-level deployment
- 多条 target-level execution

project-level deployment 表示：
- 谁触发的
- 目标 commit 是什么
- 使用什么策略
- 汇总结果是什么

target-level execution 表示：
- 这次部署下发到哪台机器
- 该机器当前状态
- 该机器的日志和错误
- 该机器实际部署到的 commit

### 6.3 状态展示

项目页需要能回答三个问题：
- 这次部署整体成功了吗
- 哪几台机器成功了，哪几台失败了
- 失败是集中在某一台，还是全部失败

这比今天的“单次部署只有一个状态”更重要。

---

## 7. 执行策略

### 7.1 all-at-once

行为：
- Core 为所有目标创建执行记录
- 所有在线 Agent 都可以领取各自任务
- 总结果按所有目标结果汇总

适用：
- 非核心环境
- 台数不多
- 用户更在意速度

### 7.2 rolling

行为：
- 按 `order_index` 顺序逐台执行
- 当前目标成功后才放行下一个目标
- 任一目标失败后，默认停止后续目标

适用：
- 生产环境
- 用户希望降低同时失败风险

这是 `v0.6` 最值得支持的方式，因为它已经能覆盖很多 2 到 5 台机器的小团队需求。

---

## 8. 技术影响范围

### 8.1 数据模型

需要改动：
- `projects` 不再只依赖单个 `agent_id`
- 增加 `project_targets`
- 增加 `deployment_targets` 或同类执行表

### 8.2 API

需要新增或调整：
- 项目目标管理 API
- 创建部署时传入发布策略
- 查询部署详情时返回每台目标机的执行状态

### 8.3 Web UI

需要补齐：
- 项目设置页维护目标机器列表
- 部署弹窗选择 `all-at-once` 或 `rolling`
- 部署详情页展示目标机执行明细

### 8.4 Agent

Agent 本身改动不会最大。

原因很简单：
- Agent 仍然只负责本机执行
- 现有 `git + docker compose` 执行模型可以复用
- 变化主要在 Core 如何分发任务、如何汇总状态

---

## 9. 风险与控制

### 9.1 主要风险

- 多机后，状态模型会明显复杂于单机
- UI 如果做得不清楚，用户会看不懂“整体状态”和“单机状态”的关系
- rolling 发布会引入顺序控制和失败停止逻辑

### 9.2 控制方式

- 先只支持单一角色的应用机，不引入 db/worker 等多角色编排
- 先只支持 `all-at-once` 和 `rolling`
- rolling 失败后默认停止，不自动做复杂补偿
- 保持 Agent 无状态执行，不把编排逻辑放到 Agent 里

---

## 10. 验收标准

如果 `v0.6` 完成，至少要满足下面这些结果：

- 用户可以在一个项目下新增第 2 台、第 3 台服务器
- 用户可以触发一次面向多台服务器的部署
- 用户可以选择并行部署或顺序部署
- 用户可以在部署详情页看到每台机器的状态、日志和错误
- 某一台失败时，整体部署结果和失败范围表达清楚
- 不引入 SSH 控制链路

---

## 11. 最终建议

版本路线建议如下：

- `v0.5`：继续收口新手友好和排障体验
- `v0.6`：不做 SSH，做多 Agent 项目的最小闭环
- `v0.7+`：再评估是否需要更强的发布策略

当前阶段最重要的不是“支持更多连接方式”，而是：

**沿着已经验证过的 Agent 架构，把单机能力自然扩展到小规模多机。**
